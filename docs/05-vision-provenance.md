# 장기 비전 — 집단 큐레이션 & 출처 그래프

> ⚠️ **이 문서는 MVP에 포함되지 않는다.** Phase 3 이후의 방향성과 가설을 정리한 비전 문서이며, MVP 단계에서는 *데이터 모델 후크* 정도만 남기고 기능은 구현하지 않는다. 1-3 가설이 통과해야만 의미를 가진다.

---

## 1. 왜 이 비전이 필요한가

Hugging Face Datasets와 Burstchester를 같은 평면에서 비교하면 지는 게임이다. 진짜 차별점은 **메타 레벨**에 있다:

| 평면 | HF Datasets | Burstchester |
|---|---|---|
| **데이터의 기원** | 1명/1팀이 만든 데이터셋의 일방적 배포 | 다수 사용자의 LLM 상호작용에서 좋은 결과를 추려낸 **집단지성 큐레이션** |
| **품질 시그널** | 다운로드 수, 좋아요 (간접) | 다운로드 + **그 데이터로 학습된 모델의 실제 평가 결과**를 다시 데이터셋에 피드백 |
| **공유 단위** | "데이터셋" | "좋은 답변을 만들어내는 데이터" — 출력 품질이 검증된 단위 |
| **추적 가능성** | 데이터셋 단독 | **데이터 → 학습된 모델 → 출력**까지의 출처 그래프 |
| **증류 모델 대비** | 둘 다 블랙박스 | **사용된 Q&A 쌍과 그 효과가 모두 공개** — 감사/재현 가능 |

## 2. 핵심 비전 — 세 개의 레이어

### 레이어 1: 집단 큐레이션 (Phase 2)
"좋은 데이터"의 정의를 단일 큐레이터의 판단이 아니라 **여러 시그널의 합성**으로 가져간다.

**시그널 종류:**
- **명시적 시그널**: 좋아요, 신고, 사용 후 후기 ("이 데이터로 학습한 모델이 좋았다/별로였다")
- **암묵적 시그널**: 다운로드 → 학습 → 모델 등록까지의 funnel completion rate
- **평가 시그널**: 학습된 모델을 작은 holdout 세트로 자동 평가 → 점수를 데이터셋에 역기록
- **사용자 평판 가중치**: 과거 업로드한 데이터셋의 후속 평가가 좋았던 사용자의 좋아요는 가중치 높음

→ **결과**: 같은 도메인의 데이터셋 100개 중 "실제로 학습 결과가 좋은" 5개가 자연스럽게 떠오른다. HF의 단순 다운로드 카운트와는 다른 차원의 큐레이션.

### 레이어 2: 출처 그래프 (Phase 3)
데이터·모델·출력 사이의 관계를 **그래프 데이터 구조**로 영구 기록.

```
┌────────────────────────────────────────────────────────────────┐
│  Dataset A (1000 rows)  ─┐                                       │
│  Dataset B (500 rows)   ─┼──► Model M1 (LoRA on llama3.1:8b)    │
│  Dataset C (200 rows)   ─┘         │                             │
│                                    ▼                             │
│                            Output O1 (eval score 0.82)           │
│                            Output O2 (user upvote 47)            │
│                                                                  │
│  Output O2 ──► (사용자가 "좋은 답변"으로 마크)                     │
│            ──► Dataset D (집단 큐레이션 시드)                      │
└────────────────────────────────────────────────────────────────┘
```

**노드 타입:**
- `Dataset` — 업로드된 데이터셋
- `Sample` — 데이터셋 내 개별 Q&A 쌍 (해시 ID로 중복 제거)
- `Model` — 학습된 모델 (사용자가 등록)
- `Output` — 모델의 출력 (사용자가 마크한 좋은/나쁜 결과)
- `User` — 작성/큐레이션한 사람

**엣지 타입:**
- `Sample → Dataset` (포함)
- `Dataset → Model` (학습에 사용됨)
- `Model → Output` (생성함)
- `Output → Sample` (좋은 출력이 새 샘플로 환류)
- `User → *` (만든이/큐레이터/평가자)

→ **결과**: "이 모델의 이 출력은 어떤 데이터에서 비롯되었나?"를 역추적 가능. **증류 모델은 절대 못 하는 것**.

### 레이어 3: 온톨로지 — 능력 ↔ 데이터의 인과 (Phase 4+, 연구성)
출처 그래프 위에 **의미 레이어** 구축.

- 데이터 샘플마다 **능력 태그(capability tag)** 자동 부여 — 예: `reasoning:chain-of-thought`, `style:concise`, `domain:legal-ko`
- 학습 후 모델 평가 결과를 능력별로 분해
- → 통계적 인과: *"`domain:legal-ko` 태그가 30% 이상인 데이터셋으로 학습한 모델은 한국 법률 QA 평가에서 평균 +12점"*
- 이게 누적되면 **"X 능력을 키우려면 어떤 데이터를 모아야 하는가"의 추천 시스템**이 된다

**경고**: 인과를 진짜 증명하려면 통제된 실험이 필요. 우리가 가진 것은 관측 데이터뿐이라 **인과 추론(causal inference)** 기법이 필수이고 학술적 난이도가 높다. 이 레이어는 **연구 파트너십이나 외부 연구자 도구로** 분리 검토.

## 3. 증류 모델과의 차별화 (스토리텔링용)

LLM 증류(distillation)는 큰 모델의 출력을 작은 모델이 흉내내게 학습하는 기법. 결과 모델은:

- ❌ 어떤 질문/답변이 학습에 쓰였는지 알 수 없음
- ❌ 특정 답변이 어떤 학습 샘플에서 비롯되었는지 추적 불가
- ❌ 데이터 라이선스 / PII / 편향성 감사 불가
- ❌ 학습 데이터를 갱신/제거 불가 (잊혀질 권리 대응 어려움)

**Burstchester로 학습된 모델은 정반대:**
- ✅ 사용된 모든 Q&A 쌍이 공개·해시 가능
- ✅ 출력 ↔ 학습 샘플의 출처 그래프
- ✅ 라이선스/PII/출처 모델 검증이 데이터 단계에서 끝남
- ✅ 특정 샘플 제거 시 "이 모델은 X 샘플을 포함해 학습됨" 표시 가능

→ **타깃 시장**: 규제 산업(금융/의료/법률), 기업 도메인 어시스턴트, 학술 연구. *"우리 모델이 무엇을 알고 있는지를 우리가 안다"*가 가치 명제.

## 4. MVP에서 미리 심어둘 후크 (가벼운 작업)

장기 비전을 위해 **MVP 데이터 모델에 다음 필드만 미리 추가**한다. 기능은 구현하지 않음.

### 4-1. Firestore `datasets/{id}` 추가 필드 (옵션, default null)

```ts
// 출처 그래프 후크
parentDatasets: string[],        // 이 데이터셋이 다른 데이터셋에서 파생된 경우 (분할/합치기)
samplingMethod: "manual-curate" | "llm-output" | "human-write" | "mixed" | null,

// 능력 태그 후크 (Phase 4 자동 분류용)
capabilityTags: string[],        // MVP에서는 비워둠. 사용자 자유 입력만
```

### 4-2. Firestore `samples/{hash}` (Phase 3에 활성화, MVP에서는 미생성)

샘플 단위 컬렉션은 Phase 3 출처 그래프 작업 시 도입. MVP에서는 **데이터셋 업로드 시 각 라인의 SHA256 해시만 메타에 기록**해 두어 추후 역마이그레이션이 가능하도록 한다.

```ts
// MVP `datasets/{id}` 메타에 추가:
sampleHashesMerkleRoot: string,  // 모든 라인 해시의 Merkle root (1개 필드)
```

→ Phase 3에서 zip을 다시 파싱하지 않고 그래프에 편입 가능.

### 4-3. Firestore `models/{id}` (Phase 2 후반에 도입)

사용자가 "이 데이터셋으로 학습한 모델"을 등록하는 컬렉션의 자리만 비워둠.

```ts
{
  ownerUid: string,
  baseModel: string,              // "llama3.1:8b"
  trainingDatasets: string[],     // dataset IDs
  trainingMethod: "lora" | "qlora" | "full",
  evalReports: { metric, score, dataset }[],   // 사용자 자기보고
  ollamaPullUrl: string | null,
  ...
}
```

## 5. 단계별 진입 트리거

| 비전 레이어 | 진입 트리거 | 진입 시 작업 |
|---|---|---|
| **레이어 1 (집단 큐레이션)** | 데이터셋 500개 + 다운로드 5k건 + "학습 후기" 자발 제출 50건 | 후기 시스템 정식화, 평판 가중치 도입, 추천 알고리즘 |
| **레이어 2 (출처 그래프)** | 등록된 학습 모델 100개 + 모델→출력 마킹 사용자 행동 발생 | 그래프 DB 도입(Neo4j or Postgres ltree), `samples` 컬렉션 활성화 |
| **레이어 3 (능력 온톨로지)** | 출처 그래프 6개월 누적 + 외부 연구 파트너 확보 | 별도 연구 프로젝트로 분리. 학술 논문 가능성 |

## 6. 위험과 한계

1. **레이어 2/3는 데이터가 충분히 쌓여야 의미가 있다.** Phase 1/2에서 충분한 사용자가 모이지 않으면 그래프는 비어있는 상태로 남고 가치가 없음 → **MVP에서 절대 미리 만들지 말 것**.
2. **인과 추론은 어렵다.** "이 데이터가 이 능력을 만들었다"는 강한 주장은 통제된 ablation 실험 없이는 약한 상관관계에 머문다 → 마케팅 카피에서 과장 금지.
3. **그래프 DB 도입은 Firebase 졸업 신호.** 이 시점에서 Postgres + Neo4j 스택으로 이전 가능성 → [`04-roadmap.md`](./04-roadmap.md) 졸업 분기점 참조.
4. **사용자 동기 부여**: 모델 등록·후기 작성은 추가 노력. 간단한 게이미피케이션(평판, 뱃지) 또는 실질 보상(유료 데이터셋 우선 접근)이 필요할 수 있음.
