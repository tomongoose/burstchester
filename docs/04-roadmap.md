## Phase 3 — 차별화 (Month 6-12)
가능한 방향 (택 1-2):

1. **자동 큐레이션** — LLM judge로 데이터셋 품질 점수 자동 산출
2. **합성 데이터 워크벤치** — 작은 시드로 큰 데이터셋 부풀리기 (Self-Instruct)
3. **유료 데이터셋 / 마켓플레이스** — 큐레이터 수익 분배
4. **클라우드 파인튜닝 button** — Modal/RunPod와 연동, "이 데이터로 1-click 학습"
5. **출처 그래프 v1 (레이어 2 시작)** — 사용자가 학습한 모델 등록 + 데이터셋 ↔ 모델 ↔ 출력 링크 — 자세한 비전은 [`05-vision-provenance.md`](./05-vision-provenance.md)
   - 진입 트리거: 등록 모델 100개 + 모델→출력 마킹 행동 관측

### 집단 큐레이션 시스템 활성화 (Phase 2 후반 ~ Phase 3)
- "이 데이터로 학습한 모델 후기" 정식 시스템 (별점 + 자유 텍스트)
- 사용자 평판 가중치 (과거 업로드의 후속 평가가 좋은 사용자의 좋아요는 가중치 ↑)
- 작은 holdout 평가 자동 실행 (Phase 3에서, Modal/RunPod 등 외부 GPU 위임)

## "Firebase 졸업" 분기점

다음 중 **하나라도 해당하면 Firebase 일부를 떠난다**:

| 신호 | 대응 |
|---|---|
| Firestore reads 비용 > $500/월 | 검색만 Postgres + Meilisearch로 분리 |
| Cloud Functions cold start이 UX 망침 (>2s 다운로드 지연) | Cloud Run으로 다운로드 패키징 이전 |
| 복잡한 권한/조직 기능 필요 | 자체 백엔드 (FastAPI/Hono) 도입 |
| 분석 쿼리 필요 (도메인별 다운로드 추이 등) | Firestore → BigQuery export, 분석은 BQ |

**Auth와 Hosting은 가장 늦게 떠난다** — 가성비가 가장 좋고 락인이 가장 약함.

## 가장 큰 불확실성 3가지 (정직하게)

1. **사람들은 정말 자기 대화를 공유할까?** — Phase 0 인터뷰 + 익스텐션 프로토타입으로 검증해야. 안 하면 시드 데이터셋 큐레이션 사이트로 피벗.
2. **로컬 파인튜닝 사용자 절대 수가 충분한가?** — Ollama MAU는 수백만이지만, "직접 학습"까지 가는 비율은 미지수. 1%만 잡아도 의미 있음.
3. **법적 회색지대를 어떻게 운영하나?** — 신고/삭제 SLA 명확화, OpenAI 출력 차단, DMCA 절차 준비.

세 가지 모두 코드 문제가 아니라 **운영·콘텐츠·법무 문제**다. 엔지니어링은 상대적으로 쉬운 부분.
