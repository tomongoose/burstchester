# 프로젝트 개요 (Burstchester)

## 1. 한 줄 정의
**LLM 사용자가 만든 "좋은 대화/생성물"을 데이터셋으로 포집·공유하고, 다른 사용자가 그것을 검색해 가져가 로컬에서 fine-tuning 할 수 있게 해주는 데이터 허브.**

비유: *"Hugging Face Datasets × GitHub × Reddit"의 LLM 파인튜닝 특화 버전*.

### 메타적 차별점 (HF 대비 본질)
- **HF는 "데이터셋 하나"를 공유한다.** Burstchester는 *"좋은 답변을 만들어내는 데이터"*를 공유한다.
- **수집 방식이 다르다**: HF는 보통 한 명/한 팀이 만든 데이터셋의 일방적 배포. Burstchester는 **다수 사용자의 LLM 상호작용에서 좋은 결과만 추려낸 집단지성 큐레이션**.
- **장기 비전**: 데이터셋 ↔ 학습된 모델 ↔ 출력 사이의 **출처(provenance) 관계를 추적 가능한 온톨로지**로 발전. 어떤 데이터가 어떤 능력으로 이어지는지 증명할 수 있는 구조.
- **증류(distillation)와의 차이**: 증류 모델은 "어떤 질문/답변으로 학습됐는가"가 블랙박스. Burstchester를 통해 학습된 모델은 **사용된 Q&A 쌍이 공개·추적 가능**하므로, 재현/감사/개선이 가능.

→ 자세한 비전은 [`05-vision-provenance.md`](./05-vision-provenance.md) (MVP와 분리된 장기 스콥).

---

## 2. 핵심 문제 (Why)
- 개인/소규모 팀이 로컬에서 LLM을 파인튜닝하려고 할 때 가장 큰 병목은 **모델이 아니라 양질의 도메인 데이터**다.
- Hugging Face Datasets는 방대하지만 **fine-tuning 친화적 포맷 정리가 안 되어 있고**, 사람들이 평소 ChatGPT/Claude/Ollama와 나눈 "쓸만한 대화"는 대부분 **개인 클라이언트에서 휘발**된다.
- "내가 LLM이랑 잘 만든 결과물 → 누군가의 파인튜닝 자산"으로 흐르는 파이프라인이 부재.

## 3. 핵심 가설

### MVP 단계 가설 (검증 필수)
1. 사용자는 **자기가 만든 좋은 prompt-completion 쌍을 한 클릭으로 공유**하고 싶어한다 (인정 욕구 + 재사용).
2. 다른 사용자는 **도메인/주제별로 잘 큐레이션된 소규모 데이터셋**(50~5000건)을 원한다 (대형 데이터셋은 오히려 부담).
3. 로컬 파인튜닝의 사실상 표준 런타임은 **Ollama**이며, "다운로드 → `ollama create`" 한 번에 끝나야 한다.

세 가설 중 하나라도 깨지면 서비스 가치가 사라진다 → **MVP는 이 세 가설을 검증하는 데만 집중**.

### 장기 단계 가설 (Phase 3+ 검증 — MVP에서는 검증하지 않음)
4. **집단지성 큐레이션은 단일 큐레이터보다 더 좋은 데이터를 만든다** (좋아요/후기/실제 학습 후 평가 시그널 누적).
5. **데이터셋 ↔ 학습 모델 ↔ 출력의 출처 그래프**를 만들면, "어떤 데이터가 어떤 능력으로 이어지는가"의 인과를 추적 가능하다.
6. **출처가 추적되는 데이터셋**은 "블랙박스 증류 모델"보다 기업/연구자에게 더 가치가 있다 (감사·재현·규제 대응).

→ 4-6은 MVP에서 검증하지 않는다. 1-3이 통과해야만 의미가 있다.

## 4. 실행 가능성 평가

### 가능한 이유 ✅
- **Ollama가 사실상의 로컬 LLM 표준**으로 자리잡아, 타깃 플랫폼이 명확함 (다음 문서 참조).
- 데이터 포맷이 이미 **ShareGPT / OpenAI messages JSONL**로 사실상 표준화됨 → 새로 만들 필요 없음.
- 핵심 기능(업로드 / 검색 / 다운로드 / 메타데이터)은 **CRUD + Full-text Search**라서 Firebase로 MVP 충분.
- LoRA + Unsloth + llama.cpp 변환 → Ollama Modelfile 파이프라인이 2026년 기준 **레시피화 완료**.

### 위험 요소 ⚠️
| 위험 | 심각도 | 대응 |
|---|---|---|
| **데이터 저작권/PII** (사용자가 ChatGPT 대화 그대로 올림) | 🔴 높음 | 업로드 시 PII 스크리너 + 동의 약관 + 신고 시스템 (MVP에서도 필수) |
| **저질 데이터 홍수** (Goodhart's law: 좋아요 = 진짜 품질 X) | 🟡 중간 | Phase 2에서 평가 메트릭 / 사용 후 별점 / "이 데이터로 만든 모델 후기" 도입 |
| **콜드스타트** — 데이터셋이 없으면 검색이 무의미 | 🔴 높음 | 초기에 **시드 데이터셋** 직접 큐레이션 (HF에서 좋은 작은 데이터셋 50개 미러링) |
| **Firebase Firestore 비용 폭증** (전문검색 N+1) | 🟡 중간 | Phase 2에서 Algolia/Meilisearch 도입 분기점 명시 |
| **법적 회색지대** (OpenAI ToS는 출력물의 경쟁모델 학습 금지) | 🔴 높음 | "오픈소스 모델 출력만 권장" 정책 + 이용약관 명시 (출처 화이트/블랙리스트는 [`03-data-spec.md` §7](./03-data-spec.md) 참조) |

### 종합 결론
**MVP 단계에서는 충분히 실행 가능하다.** 단, 기술적 난이도보다 **콜드스타트와 법적 리스크**가 더 큰 장애물이며, 이는 코드가 아니라 **운영 정책과 시드 콘텐츠**로 풀어야 한다.

## 5. MVP 범위 (3개월 1인 개발 가정)

### In-scope
1. 사용자 인증 (Google 로그인만)
2. 데이터셋 업로드 (JSONL, ShareGPT/messages 포맷)
3. 데이터셋 검색 (도메인 태그 + 텍스트 검색)
4. 데이터셋 다운로드 (`.jsonl` + Ollama용 `Modelfile` 템플릿 동봉)
5. 좋아요 / 다운로드 카운트
6. 한 가지 워크플로우만 지원: **"Ollama 사용자가 LoRA로 파인튜닝하기"**

### Out-of-scope (MVP에서 제외)
- 브라우저에서 실시간 대화 → 자동 포집 (Phase 2)
- 자동 PII 마스킹 (수동 가이드만)
- 데이터셋 버저닝
- 결제 / 유료 데이터셋
- LM Studio, llama.cpp 직접 지원 (포맷이 Ollama와 호환되지만 가이드는 Ollama만)
- 클라우드 파인튜닝 (로컬 전용)
- **출처 그래프 / 온톨로지 / 증류 모델 추적** — 별도 문서 [`05-vision-provenance.md`](./05-vision-provenance.md). MVP에서는 *데이터 모델에만 후크*를 남겨두고 기능은 만들지 않음.
- **집단 큐레이션 알고리즘 (가중치 기반 평판, 학습 후 평가 시그널 누적)** — Phase 2/3
